## 一、背景：ConstFoldLVN 留下了什么

### 1.1 "只 RAUW 不删除"带来的尾巴

ConstFoldLVNPass 遵循**职责单一**原则：它只做操作数替换（`ReplaceAllUsesWith`），**不删除任何指令**。这样做的好处在上一篇文档中已经阐明——迭代时不会让 `list` 迭代器失效，逻辑干净。

但这个设计必然产生一个后果：每次折叠/LVN 命中之后，被替换掉的那条指令仍然留在 BasicBlock 里，只是它的 `use_list_` 变成了空（没有人再使用它的结果）。举个具体例子：

```llvm
; ConstFoldLVN 后：
%v1 = mul i32 10, 200       ; use_list_ 为空 ← 死指令
%v2 = add i32 %v1, 5        ; use_list_ 为空 ← 死指令（operand 也已无效）
%v3 = sub i32 %v2, 5        ; use_list_ 为空 ← 死指令
ret i32 0                   ; 实际直接用常量 2000
```

这三条指令的 **结果值** 已经没有任何使用者，但它们还占据着 BasicBlock 的指令槽，会被 MIPS 后端老老实实地翻译成 MIPS 指令——产生完全无用的计算开销。

### 1.2 为什么需要专门的 DCE Pass

删除指令不能在 ConstFoldLVN 内随手做，原因有三：

1. **list 迭代安全**：ConstFoldLVNPass 正在 range-for 遍历 `bb.GetInstructions()`，在循环中删除当前节点会令迭代器失效（UB）。
2. **use-list 清理顺序**：删除指令前必须先对它的每个操作数调用 `SetOperand(i, nullptr)` 解挂 use-list，若 ConstFoldLVN 在 RAUW 之后立刻删，时序上很难保证 operand 中全部是"可安全 null 掉"的状态。
3. **传播链**：一条死指令死掉后，它的操作数定义指令可能也随之变成死指令（没有别的使用者了）。这种**级联传播**需要 BFS/worklist，与 ConstFoldLVN 的"替换"逻辑是两个不同的问题域。

**结论**：把"删除死指令"交给一个专门的 DCEPass，逻辑清晰，也便于后续单独开关、单独测量收益。

## 二、什么是死代码（课程教程 §（3）的 IR 级别定义）

课程教程将死代码分为两类：

| 类型 | 定义 | 例子 |
|------|------|------|
| **无用代码** | 会被执行，但结果对程序输出无影响 | `%r = mul %x, %y` 但 `%r` 的值从未被任何 output/store/return 使用 |
| **不可达代码** | 根本不会被执行到 | `BranchInst` 的条件折叠为常量后，某个后继块永远不会被跳转到 |

本 Pass 处理第一类（**无用代码**）。不可达代码的检测需要 CFG 可达性分析，留待后续扩展。

### 2.1 核心判据：指令的"有用性"

在完全 SSA 形式的 IR 下，一条指令是否有用取决于两点：

1. 它是否有**副作用**（会影响内存或控制流）
2. 它的**计算结果**是否被某条有副作用的指令（直接或间接）依赖

满足任意一点即为"有用"，否则为"无用死代码"。

## 三、算法：标记-清扫（Mark and Sweep）

### 3.1 完整算法流程

```pseudocode
Step 1 — 确定根集合（有副作用的指令，必然有用）
   roots = { 所有 ReturnInst, StoreInst, CallInst, BranchInst }

Step 2 — BFS 标记（沿 def-use 链反向传播）
   live_set = roots
   worklist = roots
   while worklist 非空:
       inst = worklist.pop()
       for each operand in inst->GetOperands():
           if operand is an Instruction in same function AND not in live_set:
               live_set.add(operand_inst)
               worklist.push(operand_inst)

Step 3 — 清扫（删除不在 live_set 中的指令）
   for each BasicBlock in func:
       collect_dead = [ inst for inst in bb if inst not in live_set ]
   for each dead_inst:
       for i in 0..dead_inst->GetNumOperands():
           dead_inst->SetOperand(i, nullptr)   // detach from operands' use-lists
       erase dead_inst from parent block
```

### 3.2 为什么从根集合"反向"传播

这是 SSA 的关键优势。在 SSA 中，每个值有唯一定义。def-use 链让我们能从"使用者"快速找到"定义者"：

- `inst->GetOperands()` 里的每个 `Value*`，如果是 `Instruction*`，就是它的直接定义者
- 从根（有副作用的指令）出发，沿 operands 向上溯源，能找到所有被根依赖的定义

这比从头扫描"谁的 use_list 为空"要精确得多——**`use_list` 为空是结果，不是原因**；根集合反向传播是正确的判断方式。

### 3.3 根集合详解

| 指令类型 | 为什么是根 | 代码中的 dynamic_cast 目标 |
|----------|------------|---------------------------|
| `ReturnInst` | 函数出口，返回值对调用者可见 | `ir::ReturnInst` |
| `StoreInst` | 写内存，副作用持久可见 | `ir::StoreInst` |
| `CallInst` | 可能有 I/O、全局变量修改等副作用 | `ir::CallInst` |
| `BranchInst` | 控制流选择，决定执行路径 | `ir::BranchInst` |

**AllocaInst 不是根**：在 Mem2Reg 之后，能被提升的 alloca 已全部消除；剩余的 alloca 是数组类型，它们的使用者（GEP、Load、Store）若有用，alloca 会被反向传播标记为活跃，不需要单独处理。

**PhiInst 不是根**：Phi 节点是纯粹的值选择，没有副作用。它若有使用者（会被其他有用指令使用），会在反向传播中被标记。若 Phi 的所有使用者都是死代码，Phi 本身也应该被删除。

### 3.4 传播时如何从 operand 找到其 Instruction 定义者

`inst->GetOperand(i)` 返回 `ir::Value*`。并非所有 Value 都是 Instruction：

- `ir::ConstantInt*`：常量，无定义指令，不需要标记
- `ir::Argument*`：函数参数，也不是指令
- `ir::GlobalVar*`：全局变量，不是指令
- `ir::BasicBlock*`：BranchInst 的操作数是 BasicBlock 指针，不是指令

因此传播时需要：

```cpp
for (size_t i = 0; i < inst->GetNumOperands(); ++i) {
    ir::Value* operand = inst->GetOperand(i);
    if (auto* def = dynamic_cast<ir::Instruction*>(operand)) {
        // 确认 def 属于同一个 Function（跨函数调用时 callee 是 Function*）
        if (def->GetParent() != nullptr && IsInFunction(def, func)) {
            // mark live
        }
    }
}
```

**注意 `CallInst` 的 `operand(0)` 是 callee（`Function*`）**：`Function` 继承自 `Constant` 而不是 `Instruction`，`dynamic_cast<Instruction*>` 会得 nullptr，自然不会被错误标记，逻辑安全。

## 四、安全删除指令的正确流程

删除指令分两步，顺序不能颠倒：

```
Step A: 解挂操作数（detach from use-lists）
   for i in 0..n-1:
       inst->SetOperand(i, nullptr)
   // SetOperand(i, nullptr) 内部会从原 Value 的 use_list_ 中 remove 这条 Use*

Step B: 从 BasicBlock 中物理删除
   bb->GetInstructions().erase(it)
   // unique_ptr 析构，Instruction 对象销毁
```

顺序约束：**必须先 A 后 B**。原因：

- 若先 erase（B），`unique_ptr` 析构，`Instruction` 对象内存已释放；
- 此时操作数对应的 Value 的 `use_list_` 中仍记录着这个已释放对象的 `Use*` 地址（悬垂指针）。
- 后续任何 RAUW 或 use_list_ 遍历都会读到悬垂指针 → UB。

这个模式在 Mem2Reg 里的 `EraseFromParent` helper 中已经使用：

```cpp
// Mem2Reg.cpp 中的 static EraseFromParent（已有）
static void EraseFromParent(ir::Instruction* inst) {
    for (int i = 0; i < static_cast<int>(inst->GetNumOperands()); ++i) {
        inst->SetOperand(i, nullptr);  // Step A
    }
    // ... erase from list  // Step B
}
```

DCEPass 将复用同样的模式（作为 pass-local static 函数，或提取为共享 utility——本次保持 pass-local）。

### 4.1 删除时的迭代器安全

同样不能在遍历 `bb.GetInstructions()` 的同时删除元素。做法：

1. **收集阶段**：第一遍遍历，把死指令的裸指针收集到 `vector<Instruction*> to_erase`
2. **删除阶段**：遍历 `to_erase`，对每个指令执行 Step A + Step B

两个阶段分开，迭代器互不干扰。

## 五、Before / After 对照

### 示例 1：常量表达式链折叠后的清扫

```llvm
; ConstFoldLVN 后、DCE 前
define i32 @main() {
b1:
    %v1 = mul nsw i32 10, 200    ; use_list 为空 ← 死指令
    %v2 = add nsw i32 %v1, 5     ; use_list 为空 ← 死指令
    %v3 = sub nsw i32 %v2, 5     ; use_list 为空 ← 死指令
    ret i32 2000
}

; DCE 后
define i32 @main() {
b1:
    ret i32 2000
}
```

3 条死指令全部消除，MIPS 后端少翻译 3 条算术指令。

### 示例 2：LVN 消除重复 mul 之后的清扫

## 六、Pass 结构设计

### 6.1 接口

```cpp
// include/pass/DCE.h

namespace pass {

class DCEPass : public FunctionPass {
public:
    bool Run(ir::Function& func) override;
    std::string_view GetName() const override { return "DCE"; }
};

} // namespace pass
```

无需持有 `Module&`（DCE 不创建常量，不需要常量池）。

### 6.2 主体结构（src/pass/DCE.cpp）

```cpp
bool DCEPass::Run(ir::Function& func):
    // Step 1: 收集所有 Instruction*
    all_insts = 所有 Block 的所有 Instruction

    // Step 2: 标记根集合
    live_set = {}
    worklist = {}
    for inst in all_insts:
        if IsRoot(inst):
            live_set.insert(inst)
            worklist.push(inst)

    // Step 3: BFS 反向传播
    while worklist 非空:
        inst = worklist.pop()
        for i in 0..inst->GetNumOperands():
            operand = inst->GetOperand(i)
            if auto* def = dynamic_cast<Instruction*>(operand):
                if def 属于本函数 AND def not in live_set:
                    live_set.insert(def)
                    worklist.push(def)

    // Step 4: 收集死指令
    to_erase = [ inst for all_insts if inst not in live_set ]

    // Step 5: 安全删除
    for inst in to_erase:
        EraseFromParent(inst)

    return !to_erase.empty()
```

### 6.3 "属于本函数"的判断

BFS 传播时需要排除跨函数的 operand（`CallInst` 的 callee 是 `Function*`，也继承自 `Value`）。判断方式：

```cpp
// Instruction* def 的 parent BasicBlock 必须在 func 的 blocks_ 中
// 简单做法：收集 all_insts 时建一个 unordered_set<Instruction*> func_insts，
// 只对 func_insts.count(def) > 0 的指令做 BFS 传播。
```

这个判断在 Step 1 收集 `all_insts` 时顺手建好，BFS 阶段 O(1) 查询即可。

## 八、main.cpp 接入模式

DCE 在 ConstFoldLVN fixpoint 循环**之后**运行一次即可：

```cpp
// ConstFoldLVN 已经在前面的 while(changed) 跑完到不动点

if (kEnableDCE) {
    pass::DCEPass dce;
    for (auto& func : result.module->GetFunctions()) {
        if (!func->GetBlocks().empty()) {
            dce.Run(*func);
        }
    }
}
```

DCE 运行后不会产生新的 ConstFoldLVN 机会（删除死指令不影响活跃指令的操作数），因此不需要外层 while 循环。

## 十、后续展望

DCE 完成后，`ConstFoldLVN → DCE` 形成完整的"无用计算消除"流水线。下一个高 ROI 的优化是：

- **O3 乘除法强度削减（MIPS 层）**：在 `InstructionEmitter` 中识别乘以/除以 2 的幂，用 `sll/sra` 替代 MIPS 的 `mul/div`；同时处理乘以小常数（3、5、7）的移位+加减组合
- **O4 窥孔优化（MIPS 层）**：在 AsmWriter 内引入滑动窗口，消除 `sw/lw` 对、`move $t,$t`、`li $t,0; addu $d,$s,$t → move $d,$s` 等冗余模式

这两项都是 MIPS 后端层面的优化，不依赖进一步的 IR pass，可以独立实施。
